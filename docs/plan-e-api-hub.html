Debate with Codex: what changed

The first draft went to Codex with the request to argue against it. Its overall verdict was agree with changes: "central hosting must not become central ownership of every product's business logic." All nine changes were adopted.

#TopicDraftCodexFinal decision
1API locationCentral platform, module per productChange Product teams should own logic and migrationsPlatform owns the plumbing. Each product owns an adapter project in its own solution.
2HostingOne host + one worker, no YARPAgree Only the worker holds DB credentialsThe API host never touches company DBs for cached datasets.
3Shared businessPorts & Adapters, keyed DIChange Semantics as executable examplesShared acceptance tests. 404 unsupported, 403 unsubscribed, startup fails if misconfigured.
4AuthOAuth2 client credentialsChange Audience per product routeCheck client, tenant, environment and grant on every call. Revocation within 60 s.
5OnboardingAdmin API + UIChange Resumable, idempotent statesPending → DbVerified → Ready → Active. Rotation from day one.
6Rate limitsPer client_idChange A second app would double the quotaBurst per app. Quota per tenant subscription, reserved atomically.

8RefreshTenant override + Hangfire lockChange Locks alone aren't enoughA generation number fences every publish.
9Reads200 + stale flag, 503 if noneChange Enforce MaxAge, pin paging?generation=N paging, 410 when expired, refresh returns 202.
03

Where the API lives

Not "each solution has its own API", and not "one solution owns every database's logic". The platform owns everything that is the same for every product. Each product owns how its business works.

ConcernLives inWhy
Identity, client registration, subscriptions, limits, quotas, refresh scheduling, admin, docs portalNew UniFreight.ApiHub.sln (.NET 10)The same for every product, written once.
Contracts: IRevenueQuery, DTOs, acceptance examplesApiHub.Contracts NuGet packageThe shared language between the platform and the products.
Business logic: how Forwarding calculates revenue, its SQL, its snapshot builderNew .NET 10 library Forwarding.ApiAdapter inside ForwardingUniFreight.Solution.slnThe team that knows the schema owns it, next to the api SP scripts it calls.
HostingThe hub loads each adapter package as a moduleOne deployment to run. An adapter can move to its own host later without code changes.

The legacy Forwarding.MvcApp (.NET 4.8) is not touched, and its /api routes are never published.

04

Shared business, different implementation

Ports & Adapters for the boundary, Strategy to choose the implementation per product, Plugin to load adapters, Template Method for snapshot builders.

// ApiHub.Contracts: one port per business capability
public interface IRevenueQuery                       // read side, served from snapshots
{
    Task<RevenueResult> GetAsync(RevenueFilter filter, TenantScope scope, CancellationToken ct);
}

public interface ISnapshotBuilder                    // refresh side, run by the Worker only
{
    string DatasetCode { get; }                      // "forwarding.revenue.daily"
    int SchemaVersion { get; }
    Task<BuildResult> BuildAsync(BuildContext ctx, CancellationToken ct);
}

// Each product registers its adapters under its product key
public sealed class ForwardingModule : IProductModule
{
    public string ProductCode => "forwarding";
    public void Register(IServiceCollection s)
    {
        s.AddKeyedScoped<IRevenueQuery, ForwardingRevenueQuery>(ProductCode);
        s.AddKeyedScoped<ISnapshotBuilder, ForwardingRevenueDailyBuilder>("forwarding.revenue.daily");
    }
}

// The platform maps the capability once for every product that registered it
app.MapCapability<IRevenueQuery>("revenue", "/{product}/v1/revenue")
   .RequireAuthorization("capability:revenue.read");

Agree on the meaning first

For example, revenue = posted invoices, net of tax, minus credit notes, converted at the posting-date rate. The rules live in Contracts/AcceptanceExamples/*.json, and every adapter must pass them in CI.

Clear failure modes

Product doesn't offer it → 404. Tenant not subscribed → 403. Subscribed but no adapter registered → the host refuses to start.

Different meaning, different capability

If Yard's storage revenue means something else, it becomes storage-revenue, not a hidden variant of revenue.

Authentication and automated onboarding

Recommendation: OAuth 2.0 client credentials with OpenIddict, not raw API keys.

API keyClient credentials → JWT (chosen)
Sent on every callA long-lived secretA short-lived token (30 min)
If it leaksValid until someone rotates itExpires within minutes
Scopes and per-product audienceCustom workBuilt in
Client toolingA custom headerAn OAuth library in every language, plus the "Authorize" button in the docs
Cost per callA hash lookupA signature check in memory

Token claims: client_id, tenant_id, env, aud (one product per token) and scope. Subscriptions stay out of the token. They are checked on every call against the cached Catalog (60 s at most), so a suspension takes effect within a minute.

Each step records its state, so a failed onboarding resumes where it stopped. Operators can rotate and revoke secrets from day one, with two valid secrets during a switchover. A self-service portal for client admins comes later.

Subscriptions, rate limits and quotas

LimitKeyed byImplementation
Burst (per second or minute)client_idASP.NET Core RateLimiter, values taken from the plan. In memory while there is one node.
Concurrencyclient_idConcurrency limiter that protects the host.
Commercial quota (day or month)Tenant subscription, all its apps togetherSQL UsageLedger with an atomic UPDATE … WHERE Used + @n <= Limit. Resets at midnight in the tenant's time zone.
Token endpointIP + client_idA separate strict limiter with lockout.

The counting rules are documented: 304 counts as 0.1 units, 429 and 5xx count as 0, and refresh requests use their own budget. Add Redis only with several nodes and a need for exact shared limits.

07

Caching

Type: refresh-ahead snapshots in SQL, with an in-memory L1 on top

OptionAssessment
Cache-aside (compute on a miss)Rejected The first caller after expiry waits for the heavy query and loads the live database.
Redis / FusionCache onlyNot alone Bound by memory, another server to run on-prem, not durable enough for data kept 48 h, and it doesn't solve date ranges.
HTTP output cacheRejected Same miss problem as cache-aside, and risky to key safely across tenants.
SQL snapshots built on a schedule + L1 memoryChosen Heavy queries run only on the schedule. The data survives restarts and company-DB outages. Uses the SQL Server you already run, and is easy to inspect.

Simple

One Snapshot database, one generic publish step, one scheduler. Each product decides only what to build.

Efficient

Reads hit indexed tables or a gzip blob, then memory on repeat. Each company database sees one heavy query per dataset per refresh interval, however many API calls arrive.

Two snapshot kinds: each product gets its own cache structure

KindUse forStorageExample
Fact snapshot (default)Anything filtered by date range, customer, branch or currencyA typed table per dataset in the product's own schema, e.g. fwd.RevenueDaily, indexed on (TenantCode, Generation, Day)Revenue for any range = SUM of daily rows. Two years ≈ 730 rows per currency.
Document snapshotFixed-shape reports returned wholecore.SnapshotDocument: tenant, dataset, partition, generation, gzip payload, ETagOpen-shipments board, aging summary

Arbitrary parameters are never a cache key. A product defines finite partitions (e.g. month=2026-10) or a daily grain. Non-additive metrics, such as distinct customers, get their own grain or become an async report.

core.DatasetGeneration (TenantCode, Env, Dataset, Generation BIGINT, Status, SourceAsOfUtc, BuiltAtUtc, RowCount, Error)
core.DatasetCurrent    (TenantCode, Env, Dataset, Generation, PublishedAtUtc)   -- the pointer readers use
core.RefreshPolicy     (TenantCode NULL, Env, Dataset, IntervalMinutes, MaxAgeMinutes, PreferredWindowUtc, Enabled)

Refresh interval per client

A default row per dataset (TenantCode = NULL) plus tenant overrides. The plan caps how often a tenant can refresh (Basic ≥ 24 h, Premium ≥ 6 h), so freshness becomes part of what a plan sells.

TenantDatasetInterval (min)Max age (min)Means
defaultforwarding.revenue.daily14401560every 24 h
UNFforwarding.revenue.daily720840every 12 h

Each company has its own database, so "per client" means per tenant, and all apps of one tenant share its snapshots. Fact builders rebuild only a watermark window (the last 45 days, which covers late postings and credit notes). A monthly full rebuild catches anything older.

    L -- hit --> OK["200 data + asOf, generation, stale=false, ETag"]
    L -- miss --> SQL["Query fact table for tenant, generation N, day range"] --> OK

L1 entries are keyed by an immutable generation, so they never need invalidating: a new publish creates new keys, and old entries age out. Paging takes ?generation=N so all pages of one sync come from the same version. An expired generation returns 410 Gone. POST /refresh (premium plans) returns 202, joins any build already running, and uses the refresh budget.

Must-haves Codex added

  • Source consistency: build under SNAPSHOT isolation or from a replica, record the true source cutoff, and rebuild a watermark window for late corrections.
  • Fleet migrations: version the api.* SPs and the fwd.* schema. The Worker refuses a tenant whose api schema is older than the adapter needs.
  • Tenant DB identity: before each build, compare Defaults.UnEditableCompanyName with the tenant code, so a typo in a server name can't serve CPW data as UNF.
  • Operations: signing-key rotation with overlap, Snapshot DB backups and restore drills, alerts on refresh lag and failed builds.
  • Tests that prove it: cross-tenant and cross-environment isolation, stale-worker publish, concurrent quota reservation, load tests on reads and refreshes.
